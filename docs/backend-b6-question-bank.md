# B6 categories and question bank

**2026-10-27 response-format update:** question APIs and both editors now support the approved written/MCQ model. See [response definitions and rollout](interview-response-definitions.md). Active written questions require rubrics; MCQs are allowed for Technical, Situational, and Coding and cannot have explanations. Student projections exclude answer keys. This update supersedes the original field list/readiness marker below; readiness now requires migration `202610270002`.

Contract: authenticated `GET /api/categories` returns active categories with an explicit ordered `phases` configuration and derived `pipeline` label. Admins with `questions:write` use `GET/POST /api/admin/categories`, `PATCH /api/admin/categories/{id}`, `GET/POST /api/admin/categories/{id}/questions`, and `PATCH /api/admin/questions/{id}`. Lists accept `page` and `pageSize` (1–100); admin lists also accept `status=active|inactive`. Unknown and repeated query fields are rejected. Mutations require the existing session and CSRF protections; writes and audit records commit together. No hard delete is exposed.

Category fields: name (1–120), description (0–2000), color/bg (#RRGGBB), status, phases. Each phase has a unique id (lowercase letters/hyphens, 1–40), label/shortLabel (1–80), supported question types, and count (1–5). There are 1–8 phases, no type may appear in multiple phases. Default: Introduction ×1, Technical ×2, Candidate Questions ×1. New categories remain unavailable until their bank satisfies that configuration. PATCH is partial and rejects empty/unknown fields.

Question fields: question (1–12000), type, hint (0–4000), feedback (private rubric, 0–12000), status. Supported types: Introduction, Technical, Behavioral, Situational, Motivational, Coding, Design Challenge, Candidate Questions. This explicitly extends the earlier enum with Design Challenge before importing the UX exercise.

`GET /api/categories/{id}/pipeline` selects active questions on the server in phase order, without replacement, with randomized selection within each phase. It returns only id/question/type/hint, never feedback or status. Inactive categories return 404. Insufficient active questions return 409 `CATEGORY_UNAVAILABLE`; no browser fallback or silent count reduction. Selection locks the category and questions against concurrent edits until the response snapshot has been assembled. This is a practice preview, not a persisted attempt; B7 will reuse selection inside attempt creation and store immutable snapshots.

Seed content is stored server-side with deterministic UUID mappings from the original category slug and question position. It includes introduction, situational fallback and closing prompts, plus practical challenges; no people or credentials. Import is operator-run, transactional and repeat-safe without overwriting later edits. The original teaching prompts are retained, not certified as a production evaluation standard. Review rubrics before hosted rollout.

Deployment: apply `202610140001_b6_question_bank.sql` after B5, then run `supabase/seeds/b6_question_bank.sql` as the operator. Deploy API and frontend together. Hosted migration, seeded content review and hosted acceptance are separate from local verification. B7 persistence/scoring is not implemented by this phase.

The API readiness marker now requires `202610140001`. Do not deploy the API ahead of that migration. Regenerate the seed offline with `node --import tsx scripts/prepare-b6-seed.ts`; its UUID mapping is in `apps/api/content/b6-uuid-map.json`. Runtime selection uses only database phase configuration; the offline generator records the legacy categories' initial configuration. Source teaching material lives under `apps/api/content`, outside the frontend import tree.

The administrator editor supports ordered phases, per-phase types/counts, question rubrics, and status changes. Student practice uses the preview endpoint and records responses in memory only. Random scores and claims of completed AI evaluation were removed. A category shortage is shown to the student; no hidden fallback is used.

Local verification uses embedded PostgreSQL with real migrations/runtime grants and HTTP transport tests. It covers seed repeatability, every seeded pipeline, CRUD persistence, deactivation/shortages, safe student projections, validation, authorization, revoked accounts, audit rollback, pagination and CSRF. Multi-connection races and hosted Supabase behavior still require staging acceptance. OpenAPI B6 operations and local Postman requests are generated by `scripts/update-b6-artifacts.mjs`; the collection has not been pushed or run against a hosted service.

Verified locally on 2026-10-14 using the repository's Node 22 runtime: 66 API tests and 17 frontend/proxy tests passed; the focused B6 tests passed again after the final rubric-permission guard. API and Next.js production builds passed. The Chrome smoke test passed with isolated HTTP fixtures, including pipeline shortage/recovery, admin phase/question saving and role-specific rubric visibility. `node tests/b6-bundle-check.mjs` confirmed all 48 source rubrics were absent from 17 built JavaScript assets. The system Node 24 run failed in an existing B4 multipart-stream test; the supported Node 22 run passed. No hosted database or deployment was changed.
